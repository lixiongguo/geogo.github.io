## WebAR 导航：WebAssembly 遇到过什么问题？

**背景（简历）**：自研 SLAM / VPS C++ 核心编译为 Wasm，浏览器内跑特征跟踪与位姿估计；相机帧 Web 取流 → Wasm → 6DoF → three.js 渲染。

**分工**：Wasm = 跟踪与位姿；three.js / WebGL = AR 叠加；坐标系对齐在 JS / 场景侧完成。

### 1. 性能 / 帧率（最容易问）

- **问题**：特征提取、匹配、位姿求解在 Wasm 里比 Native 慢；手机 WebView 更紧。
- **答法**：说清瓶颈在哪（图像处理 / 矩阵 / 内存拷贝，而不是「Wasm 天生慢」）；做过降分辨率、限帧、轻量特征、热路径留在 Wasm、UI/渲染留在 JS；用性能档位适配中低端机。

### 2. JS ↔ Wasm 数据拷贝（很加分）

- **问题**：每帧图像 buffer 跨边界拷贝，有时比算法本身还贵。
- **答法**：减少拷贝次数；预分配 buffer / 只传必要 ROI；位姿用少量 float 回传，不要大块中间结果来回传。

### 3. 内存与稳定性

- **问题**：Wasm 线性内存上涨、长时间导航泄漏；iOS Safari / 微信内存杀进程。
- **答法**：关键复用、限制地图/关键缓存规模、会话结束主动释放；OOM 时降质或回退纯 VPS / 低频重定位。

### 4. 多线程与阻塞主线程

- **问题**：重计算堵主线程 → 卡顿、预览掉帧；`SharedArrayBuffer` / pthread 在微信里常不可用或受限。
- **答法**：承认 WebView 限制，多数情况单线程或 Web Worker；算法做时间预算（单帧超时则跳帧）；未真正做过就不要吹「开了多线程」。

### 5. 工具链与体积

- **问题**：Emscripten 编译、依赖裁剪、`.wasm` 体积大导致首屏慢。
- **答法**：关掉无用模块、优化编译、按需加载；首包与定位模块拆分。

### 6. 调试难

- **问题**：C++ 崩在 Wasm 里难查，微信里更难抓栈。
- **答法**：分层日志（JS 侧帧率/位姿健康度 + Wasm 侧关键数/跟踪状态）；先 Chrome 桌面复现，再收窄到真机 WebView。

### 7. 坐标系 / 时序（业务强相关）

- **问题**：相机时间戳与位姿不同步、横竖屏/内参变化导致「飘」。
- **答法**：严格说不全是 Wasm——Wasm 出局部位姿，JS / three.js 做 VPS ↔ SLAM ↔ 场景标定；表现是穿地/漂移，根因在标定与时序。

### 30 秒标准答

> 主要坑有三类：一是每帧图像进 Wasm 的拷贝和算力，手机 WebView 上容易掉帧，我们做了降分辨率、限帧和性能分档；二是长时间运行的内存与微信/iOS 杀进程，缓存和关键要控规模；三是调试和线程限制，重计算尽量不堵死渲染，定位状态和 JS 侧监控分开。渲染用 three.js，Wasm 只负责跟踪和位姿输出。

**若追问「最难的一个」**：优先讲 **跨边界拷贝 + 真机帧率**，比「编译报错」更像做过端上项目。
