## 2. 当前 Agent 流程

主要调用链：

**聊天 API → ChatService → AgentRunner → LLM 选择工具 → MCP 执行 → 更新本轮数据 → 再次决策 → 生成回答 → 保存会话。**

具体行为如下：

1. **准备会话。**
   `ChatService._prepare_answer()` 从 MySQL 加载历史消息和 `query_context`；必要时生成滚动摘要。
2. **发现工具。**
   `AgentRunner.stream()` 调用 `MCPClientManager.discover_tools()`，获得工具名称、描述和参数 Schema。
3. **动态决策。**
   `LLMProvider.complete_messages()` 将消息和工具定义发送给模型，由模型返回 `tool_calls`。
4. **约束参数并执行。**
   `AgentRunner._bind_call()` 注入当前知识库范围；`_ensure_table_catalog()` 和 `_validate_table_choice()` 约束 Excel 选表。
5. **更新本轮状态。**
   `_apply_tool_result()` 收集检索片段、Excel 结果、引用、警告和澄清候选，并将工具结果加入后续模型上下文。
6. **结束或请求澄清。**
   工具返回 `needs_clarification` 时提前返回；正常结束时通过 `stream_messages()` 生成回答。

当前配置为最多 **3 轮规划、4 次工具调用**。模型第一次没有选择工具时，还存在自动调用检索或 Excel 工具的兜底逻辑。见 [AgentRunner.stream() (line 100)](D:/python_project/rag_demo/backend/app/chat/agent.py:100) 和 [config.yaml](D:/python_project/rag_demo/backend/config.yaml)。

因此，当前已经是**有限轮次的动态工具调用 Agent**；但业务任务状态主要隐含在消息中，没有独立的审计目标、信息缺口和完成条件。

# 二、目标架构理解

## 1. 整体职责边界

根据方案，推荐建立以下边界：

- **LangGraph：** 保存任务状态，执行节点，依据状态路由，处理暂停、恢复和结束。
- **Decision Agent：** 使用 LLM 判断当前缺什么、下一步做什么。
- **LlamaIndex：** 组织文档接入、Node、索引、检索及知识上下文。
- **Tool：** 执行确定性的查询、读取、计算和报告生成操作。
- **数据层：** 保存业务事实、证据原文、执行记录及缓存。

这里需要准确区分：**动态规划由 Decision Agent 的模型与规则共同完成，LangGraph 负责承载和执行这一机制。**

六个 Agent 可以先实现为同一应用中的图节点，共用模型服务；不必立即拆成六个独立部署服务。LangGraph 节点也可以直接执行普通函数，数学分析节点无须额外调用 LLM。[LangGraph Graph API](https://docs.langchain.com/oss/python/langgraph/graph-api)

## 2. LangGraph 层

### State 设计

保留文档提出的九个字段，但建议明确类型和更新规则：

| 文档字段              | 推荐含义与约束                                        |
| --------------------- | ----------------------------------------------------- |
| `question`            | 原始问题，任务内保持稳定                              |
| `goal`                | 结构化目标，包括审计对象、范围和输出要求              |
| `stage`               | 明确的阶段枚举，由节点执行结果更新                    |
| `evidence`            | 结构化证据集合，按证据 ID 去重，包含来源、版本和定位  |
| `missing_information` | 尚未满足的信息项，包含重要程度与解决状态              |
| `executed_tools`      | 工具执行记录，包含调用 ID、参数、状态、结果引用和错误 |
| `analysis`            | 分析结论、计算结果和依据映射，避免只保存自由文本      |
| `next_action`         | 受约束的动作枚举，配合经过校验的参数                  |
| `finished`            | 由终止条件确定，不能仅由模型随意设置                  |

还需要补充四组运行字段：

- **身份与范围：** `task_id`、`run_id`、`conversation_id`、知识库及授权数据范围。
- **中间结果：** 多次 SQL/Excel 查询结果引用、文档检索结果引用、分析结果。
- **运行控制：** 步数、调用预算、错误、重试、停止原因、待澄清内容。
- **可追溯信息：** State 版本、模型/Prompt/工具版本、报告 ID。

State 应保存可序列化数据。数据库 Session、客户端、模型实例、完整 PDF 和大表结果应留在状态外，通过依赖或结果 ID 访问。

证据、工具记录和消息需要定义合并规则，避免后续节点覆盖先前结果。持久化需显式配置 checkpointer 和稳定的 `thread_id`，才能实现按任务暂停与恢复。[LangGraph Persistence](https://docs.langchain.com/oss/python/langgraph/persistence)

### Graph 节点与 Agent 职责

| 节点            | 职责                                               | 主要输出                 |
| --------------- | -------------------------------------------------- | ------------------------ |
| Supervisor      | 理解目标、提取已知条件、初始化任务及范围           | 初始 State               |
| Decision        | 检查信息缺口、选择下一动作、判断是否需要澄清或结束 | 动作、参数、简短决策说明 |
| SQL Agent       | 获取真实表结构，构造并执行受控采购查询             | 结构化事实及查询来源     |
| Retrieval Agent | 使用 LlamaIndex 查找制度、合同、规范和审计资料     | 带定位的文档证据         |
| Analysis 节点   | 调用 Excel 统计、价格比较等确定性工具              | 计算结果和适用条件       |
| Audit Reasoning | 综合事实、条款、参数和计算结果，处理冲突与不足     | 审计发现、依据、待复核项 |
| Report          | 根据已有结论和证据生成报告                         | 结构化报告及展示内容     |

方案总图中的 `Analysis Agent` 没有独立章节定义。建议先解释为**确定性分析节点**，与负责综合判断的 Audit Reasoning Agent 分开。

推荐执行关系：

**Supervisor → Decision → 被选中的执行节点 → 更新 State → Decision。**

其中：

- 信息缺失且可以获取：继续查询或检索。
- 信息缺失且需用户补充：暂停任务。
- 已具备分析条件：进入 Audit Reasoning。
- 审计分析发现新缺口：返回 Decision。
- 满足报告条件：进入 Report。
- 完成输出：结束。
- 预算耗尽或服务失败：记录停止原因，输出阶段结果或信息不足说明。

SQL、RAG、Excel 均为按需分支，不要求每次全部执行。

### Decision 机制

建议采用“模型提出动作，程序检查动作”的方式：

1. 输入当前目标、证据摘要、信息缺口、可用工具及剩余预算。
2. 模型输出结构化动作及参数。
3. 程序检查动作是否合法、范围是否允许、参数是否完整。
4. 检查是否重复执行相同且无新增信息的动作。
5. 执行后记录成功、空结果或错误，更新信息缺口。
6. 用明确的完成条件控制报告生成。

`finished` 还不足以区分正常完成、证据不足、等待补充和执行失败，建议增加 `status`、`stop_reason`。

## 3. LlamaIndex 层

| 模块             | 推荐实现                                                     |
| ---------------- | ------------------------------------------------------------ |
| Document Loading | 读取现有解析结果，将 `ParsedDocument`、`DocumentBlock` 转换为 LlamaIndex Document；继续复用 MinIO 和解析器 |
| Node Parser      | 适配现有结构化切块，保留章节、表格、页码和定位；正文与 Excel Schema 使用不同策略 |
| Embedding        | 首先适配现有 BGE-M3 服务；显式配置模型，统一入库与查询的模型版本、维度和文本处理方式 |
| Index            | 组织 Node 与文档版本、内容哈希、索引版本的关系               |
| Retriever        | 保留 BM25、向量召回、RRF、精确编号匹配和重排能力，逐步纳入 LlamaIndex 抽象 |
| Vector Store     | 对接 Elasticsearch，显式映射正文、向量、Metadata、Node ID 和文档 ID |

LlamaIndex 的 `IngestionPipeline` 可以组织转换、Embedding 和入库，并提供转换缓存；业务版本管理及多存储一致性仍需项目自行设计。[LlamaIndex Ingestion Pipeline](https://developers.llamaindex.ai/python/framework/module_guides/loading/ingestion_pipeline/)

两个实施注意点：

- **PDF 不需要重新搭建 OCR。** 应从现有 MinerU/PP-Structure 输出开始接入 LlamaIndex，避免重复解析和丢失坐标。
- **旧 ES 索引不能仅靠替换连接类完成迁移。** 当前 `content`、`embedding`、顶层结构字段及关闭索引的 `metadata` 对象，需要与 LlamaIndex 的 Node 序列化、过滤和读取方式逐项适配。连接器支持字段配置，但不代表旧数据天然兼容。[LlamaIndex ElasticsearchStore](https://developers.llamaindex.ai/python/framework-api-reference/storage/vector_store/elasticsearch/)

文档中的 HuggingFace Embedding 接口属于一种部署选择。当前使用 Ollama 提供 BGE-M3，建议先保留服务接口，避免同时引入新的模型加载方式和资源占用。

4. 在新索引上验证 ElasticsearchStore 的读写、过滤和删除。
5. 加入 Schema Document 检索。

**验收：** 页码、坐标、表格范围和引用不丢失；精确编号检索与混合召回无明显回退；新旧索引可切换。

## 阶段 4：Tool 体系重构

**目标：提供可独立测试的查询、检索、读取、计算和报告渲染工具，并统一证据结构。**

### 1. Agent 与工具的边界

| Agent 层：允许使用 LLM | Tool 层：不调用 LLM          |
| ---------------------- | ---------------------------- |
| 根据问题选择数据表     | 返回真实表结构和字段说明     |
| 根据 Schema 生成 SQL   | 校验并执行 SQL               |
| 生成检索问题和过滤条件 | 执行检索，返回原始片段和定位 |
| 生成 Excel 查询计划    | 执行过滤、聚合、排序         |
| 确定价格比较条件       | 校验输入口径并计算指标       |
| 综合证据形成审计判断   | 返回事实、计算结果和执行记录 |
| 撰写报告内容           | 校验报告结构、渲染和保存文件 |

工具发现参数不足、执行失败或结果存在歧义时，返回结构化状态，由 Agent 决定补充参数、重新调用或询问用户。

### 2. 工具契约调整

| 工具                           | 输入                                   | 执行内容                                             |
| ------------------------------ | -------------------------------------- | ---------------------------------------------------- |
| `retrieve_database_schema`     | 检索词、数据源范围、可选表名           | 从真实元数据和已登记说明中查找表、字段及关系         |
| `query_purchase_database`      | SQL、绑定参数、数据源标识              | 权限与语句校验、只读查询、结果限制                   |
| `retrieve_documents`           | 检索词、过滤条件、Top-K                | 按配置执行召回、融合和重排，返回证据片段             |
| `read_original_document`       | 文档 ID、版本、页码或块定位            | 读取指定原文、表格和图片                             |
| `analyze_purchase_excel`       | 表 ID、结构化查询计划                  | 精确执行筛选、分组、聚合、排序                       |
| `analyze_price_reasonableness` | 当前价格、可比样本、单位口径、规则标识 | 计算统计指标和偏差；配置了明确规则时返回规则命中结果 |
| `generate_audit_report`        | 完整结构化报告、证据引用、模板和格式   | 校验、渲染、保存，返回报告 ID 和文件位置             |

其中：

- Excel 工具不再接收自然语言问题并自行生成计划。
- 价格工具不自行判断技术可比性或生成综合审计结论。
- 报告正文由 Report Agent 生成。报告工具建议命名为 `render_audit_report`，突出渲染职责。
- 文档检索可保留现有 Embedding 和重排模型，但不在工具内增加生成式 LLM 改写、摘要或推理。

### 3. 开发顺序

1. **统一工具契约。** 定义输入 Schema、结果、证据、错误和执行记录；授权范围由服务端注入。
2. **实现 Schema 检索与 SQL 执行。** SQL Agent 生成 SQL，工具负责校验和只读执行。
3. **适配 Excel。** 将现有 `ExcelQueryService._llm_plan()` 的职责移到 Agent 层；工具接收已经生成的 `ExcelQueryPlan`。
4. **暴露原文读取。** 返回原始内容及版本定位，解释和信息提取由 Agent 完成。
5. **实现价格计算与报告渲染。** 计算采用明确公式及规则；渲染使用 Agent 提供的完整内容。
6. **接入 State。** 由图节点将工具结果、证据引用和执行状态合并进 AuditState。

统一返回包含：`status`、`data/result_ref`、`evidence`、`warnings`、`error`、`execution`。工具不负责修改全局目标或决定下一步动作。

### 4. 验收要求

- **关闭生成式 LLM 服务后，使用已准备好的合法参数，所有工具仍能独立执行。**
- 工具执行路径不调用 LLM，也不通过其他服务间接调用 LLM。
- 越界或无效请求返回明确错误，不自动猜测或修正业务意图。
- 相同输入、相同数据版本和配置下，计算结果可复核；检索结果按固定配置验证。
- 原始数据和计算结果均携带来源；报告中的结论具有对应证据引用。
- Agent 负责选择下一步，工具负责完成本次明确操作。

## 阶段 5：数据处理升级

**目标：完成真实数据导入、证据版本和生产索引迁移。**

开发顺序：

1. 落实采购业务表、字段映射和导入规则。
2. 将现有 Excel 结构化行迁移到业务数据通道。
3. 构建表 Schema 的语义索引。
4. 完善 PDF 结构到 Node 的映射及质量复核。
5. 建立原文件、解析结果、业务行、证据和报告之间的版本关系。
6. 分批重建索引，校验后发布。

**验收：** 导入行数、数量和金额能够对账；重复导入可控；旧报告仍可定位其使用的证据。

业务表与 Metadata 的设计应在阶段 2～3 提前完成，阶段 5 执行完整迁移，避免阶段 4 的 SQL 工具无数据契约可依赖。

## 阶段 6：评估和测试

**目标：验证整个采购审计闭环。测试应贯穿前五个阶段，此阶段完成系统验收。**

| 维度       | 验证内容                                                   |
| ---------- | ---------------------------------------------------------- |
| 路由决策   | 纯 SQL、纯检索、Excel、混合审计、信息不足、重复调用        |
| 检索       | 证据 Recall@K、编号准确性、制度版本、引用定位              |
| 结构化查询 | 金额与数量准确性、跨表关系、单位与币种、空值及公式缺失     |
| PDF/Excel  | 文本 PDF、扫描件、复杂表格、多 Sheet、多表区域及低质量输入 |
| 审计结论   | 可比性检查、冲突证据处理、结论与依据对应、信息不足时的表达 |
| 恢复能力   | 节点失败、进程重启、用户澄清、重复请求、SSE 断线           |
| 真实集成   | 本地模型 Tool Calling、MySQL、ES、Redis、MinIO、GPU Worker |
| 性能       | 总耗时、工具调用次数、上下文消耗、并发与大表处理           |

建议保留现有测试作为回归基础，增加经人工复核的采购问题与标准结果集。验收阈值需要根据数据规模和业务要求确定。

# 六、实施前需要确认的问题

以下信息无法从当前代码和方案确认，会影响数据库设计、部署和审计规则：

1. **采购数据源：** 是否已有独立采购 MySQL 数据库？`contract_excel` 是现存表还是拟新增表？需要确认真实 DDL、表关系以及 Excel 字段样例。
2. **业务口径：** 价格合理性采用哪些可比条件和风险阈值？金额是否含税、是否涉及多币种、运费和不同配置？
3. **审计范围：** 本期是否包含供应商风险和制度合规？对应的数据来源、制度版本及适用规则是什么？
4. **运行环境：** 实际 Redis 是否具备所需模块？本地模型的准确版本和 Tool Calling、图像输入能力是什么？
5. **交付与规模：** 报告需要聊天展示、结构化 JSON，还是 Word/PDF 文件？预计文件量、最大 Excel 行数、并发用户数及是否要求多用户权限隔离？
