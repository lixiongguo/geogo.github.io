> 端侧拍照 / 视觉算法：算力、带宽、功耗、热都封顶，却要出「旗舰观感」。口诀——**有限资源尽可能榨干：用破自行车跑出法拉利的效果**。  
> 方法论：**Profiling → 取舍 → 阉割**；工具以 **Perfetto / SimplePerf** 为主；对象分 **CPU / NPU / GPU / DSP**。

---

## 1. 心态与目标

手机不是工作站：同一颗 SoC 上相机、ISP、显示、系统服务抢资源。优化不是「算法无限堆」，而是：

| 维度 | 常见约束 |
| :--- | :--- |
| 时延 | 预览帧率、拍照点击到出图、夜景多帧合成 |
| 吞吐 | 单位时间处理帧数 / 分辨率 |
| 功耗 / 热 | 长录、连拍、HDR 连开后降频 |
| 内存 / 带宽 | DDR 带宽打满比算力先爆更常见 |

**目标要可测**：例如「预览 30fps 不掉帧」「夜景端到端 < Xs」「NPU 利用率 > Y% 且 CPU 不空转等」。没有数字，就无法判断主次矛盾。

---

## 2. 优化对象：CPU / NPU / GPU / DSP

不同单元擅长不同事；**错放算子 = 白优化**。

| 单元 | 擅长 | 拍照里常见用法 | 易踩坑 |
| :--- | :--- | :--- | :--- |
| **CPU** | 控制流、不规则逻辑、小数据调度 | Pipeline 编排、后处理 glue、部分几何/过滤 | 大卷积、密集像素算放 CPU 必炸；线程抖动影响帧时 |
| **NPU** | 规则张量、CNN/Transformer 推理 | 检测、分割、超分、降噪网络 | 不支持的算子回退 CPU；频繁 host↔device 拷贝；batch/布局不合加速器 |
| **GPU** | 并行像素、纹理、部分通用计算 | 滤镜、融合、warp、部分 ISP-like 着色器 | 与 UI/合成抢 GPU；带宽敏感；同步点过多 |
| **DSP** | 定点、流式信号、固定核 | 传统 ISP 块、音频旁路类流水、部分预处理 | 工具链与精度约束；和 CPU 共享内存一致性要小心 |

**实践原则**

1. **热路径放对硬件**：重网络 → NPU；大图规则像素 → GPU/DSP；分支多、量小 → CPU。  
2. **减少跨设备搬运**：拷贝与格式转换（NHWC↔NCHW、FP16↔INT8、stride）经常比算子本身更贵。  
3. **流水线重叠**：sensor 取流 / ISP / 推理 / 后处理尽量 **pipeline**，别串成「等上一段完全结束」。  
4. **看整机而不是单核**：NPU 跑满但 CPU 单核 100% 调度，帧率照样掉。

## 3. 工具：Perfetto 与 SimplePerf

没有 profiling 的「感觉优化」多半是错的。

### Perfetto

系统级 **trace**：CPU 调度、进程/线程、ftrace、部分 GPU/显示、自定义 track。适合回答：

- 掉帧时谁在跑？是谁阻塞了谁？  
- 相机 pipeline 各段墙钟时间如何重叠？  
- 锁竞争、唤醒延迟、binder 是否拖后腿？

用法直觉：抓一段「点拍照 / 预览卡顿」的 trace → 对齐帧时间线 → 标出长切片与空隙（空等 = 同步或排队问题）。

### SimplePerf

偏 **CPU 采样 / 计数器**：热点函数、调用栈、cache miss、部分 PMU。适合回答：

- 这个 C++/Java 模块里哪几个函数吃 CPU？  
- 是计算重还是内存访问差？

**分工**：先 Perfetto 定「系统级主矛盾」（调度？拷贝？某核打满？），再用 SimplePerf 钻进热点函数。只有算法侧时，再配合厂商 NPU/GPU profiler（算子耗时、DDR、利用率）。

## 4. 学会取舍：主要矛盾 vs 次要矛盾

资源有限时，优化列表永远做不完。判断顺序建议：

1. **用户可感知指标**：掉帧、出图慢、发热杀进程 —— 先于「某算子再快 5%」。  
2. **占比最大的墙钟时间**：Pareto——前 20% 模块往往占 80% 时延。  
3. **可改动成本**：改分辨率/跳帧/量化往往比重写算法快出效果。  
4. **质量底线**：哪些画质指标不可破（噪点、细节、伪影），哪些场景可降级（弱光再开重模型）。

常见取舍例子（拍照）：

| 手段 | 换来什么 | 可能丢掉什么 |
| :--- | :--- | :--- |
| 降预览推理分辨率 | 帧率、功耗 | 小目标 / 边缘精度 |
| 多帧 → 少帧 / 自适应帧数 | 时延、热 | 极暗画质 |
| INT8 / 稀疏 | NPU 吞吐 | 难例精度 |
| 异步流水、丢中间帧 | 流畅度 | 偶发结果滞后一帧 |
| 高端机全开、低端机阉割档 | 机型覆盖 | 体验一致性 |

**主要矛盾**随场景变：预览卡多半是实时路径；成片慢多半是多帧+大模型；发热则是持续高负载与电压墙。先定性再动手。

## 5. 步骤：Profiling → 取舍 → 阉割

固定三段，避免一上来「乱改代码」。

### （1）Profiling

- 复现卡点（固定机型、固定场景、固定版本）。  
- Perfetto 看端到端与调度；SimplePerf / 算子 profile 看热点。  
- 记下：**时间线、占比、是否带宽/同步瓶颈**（不只是 FLOPs）。

### （2）取舍

- 列出候选杠杆（算力换画质、分辨率、帧数、精度、是否走 NPU）。  
- 用产品 / 画质同学对齐：**哪些可砍、哪些必须保**。  
- 选 **ROI 最高** 的一两刀，不要同时改十处导致无法归因。

### （3）阉割（有策略的减负）

「阉割」不是贬义，是端侧常规手段：在可接受质量下减负。

- **模型侧**：剪枝、蒸馏、低比特、更小 backbone、按场景切换 lit/heavy 模型（见压缩分享：剪枝 / 量化 / 蒸馏）。  
- **数据路径**：ROI 推理、降采样、跳帧、缓存上帧结果。  
- **功能侧**：低端机关掉次要特效；高温时自动降档。  
- **实现侧**：合并 kernel、去掉多余同步、复用 buffer、避免每帧 alloc。

然后 **再 profile**：确认主矛盾真的挪了；画质回归；再进入下一轮——形成「小型化 ↔ 精度」正循环（压小 → 腾出算力加回效果 → 再压）。

```text
复现卡点
  → Profile（Perfetto / SimplePerf / 器件 profiler）
  → 判断主矛盾（算力 / 带宽 / 同步 / 调度）
  → 取舍（保哪些画质，砍哪里）
  → 阉割或换硬件映射
  → 复测指标 + 画质
  → 下一刀
```

## 6. 和模型压缩的衔接

性能优化常落到模型体积与算力：

| 瓶颈感知 | 优先手段 |
| :--- | :--- |
| 计算量 / 时延 | 结构变轻、蒸馏、算子融合、上 NPU |
| 内存占用 | 量化、分块推理、释放中间激活 |
| 参数量分布不均 | 剪枝、通道裁剪 |
| 精度掉点 | WarmUp、难例加数据、场景 case-by-case 回退 FP |

压缩是「阉割」的一类工具；**先 profile 再压**，避免在不是瓶颈的模块上剪枝。

---

## 一句话

端侧拍照优化 = **认清 CPU/NPU/GPU/DSP 分工** + **Perfetto/SimplePerf 找主矛盾** + **敢取舍、敢阉割**，在画质红线内把有限硅片当成法拉利来开。
