2.3 启发因子的选择

常见启发函数有两种：

  • 欧几里得距离：适合连续空间
  • 曼哈顿距离：适合规则网格，如战棋类游戏

在连续空间中，最常用的是欧几里得距离。为了节约计算量，工程上常直接使用距离平方。

重点：
单一目标搜索优先用 A*；
如果要从一类目标中找最近实例，则更适合使用 Dijkstra。

3. 导航图的构造

为了使用图搜索算法，必须先把游戏地图转换为图结构。常见方法有两类。

3.1 基于单元的导航图

把地图均匀划分为网格，每个格子对应一个节点，相邻格子之间建立连边。

优点：

  • 信息细致
  • 容易表达地形和阻挡属性

缺点：

  • 图规模增长很快
  • 节点数和边数都很大
  • 大地图和多 AI 同时搜索时，时间与空间开销都很高

3.2 基于可视点的导航图

通过人工安置关键节点，并在彼此可见的节点之间建立连边，构造导航图。

优点：

  • 图规模较小
  • 易于嵌入”有意义的位置”，如掩体、伏击点、狙击点

缺点：

  • 强依赖人工布点
  • 需要地图设计者持续维护和调整

4. 游戏中的寻路模块

寻路是 AI 系统的基础模块，许多行为逻辑都会依赖它。

在这个项目中，寻路模块主要由两部分组成：

  1. 导航图构建
  2. 图搜索算法

4.1 算法选型

根据目标类型不同，选择不同算法：

  • 单一目标：使用 A*
    因为 A* 能借助启发函数更有针对性地逼近目标。

  • 目标是一类物品（如药品、武器）：使用 Dijkstra
    因为它能构造最短路径树，从而找到最近的实例。

4.2 导航图选型

本项目采用 基于可视点的导航图，主要是因为：

  • 场景复杂，需要在图中布置多个有语义的关键位置
  • 地图规模较大，若使用网格图会占用过多资源
  • 在移动端平台上，网格导航图的代价通常过高

因此，导航节点主要由策划设计，美术参与整体导航图制作。

4.3 A* 启发函数设计

本游戏使用 欧几里得距离 作为 A* 的启发因子。
由于地图空间是连续的，为了节约资源，实际实现中使用的是距离平方。

5. 工程实现细节

5.1 索引优先队列

A* 和 Dijkstra 都依赖优先队列。

如果直接把”当前累计开销”写入图节点，会有两个问题：

  • 会破坏原有图结构
  • 多个搜索同时运行时，节点数据会互相干扰

因此更合适的方式是使用 索引优先队列：

  • 队列中存放节点索引
  • 节点对应的代价保存在外部数组中
  • 出队时返回索引，再访问实际节点

这样既不需要修改图结构，也更适合多搜索任务并存。

5.2 时间片规划

为降低 CPU 峰值开销，可以把一次完整搜索拆成多个时间步骤，分散到多个更新帧中执行。

这类似操作系统中的”时间片轮转”：

  • 每一帧给所有活跃搜索分配固定预算
  • 每个搜索只执行若干个搜索周期
  • 搜索完成或失败后再通知对应 AI

一次搜索周期通常包括：

  1. 从优先队列中取出下一个节点
  2. 将该节点加入最短路径树
  3. 检查它是否为目标节点
  4. 若不是，则检查其邻接节点并进行边放松

把整次搜索拆成多个搜索周期后，就能把寻路任务均匀摊到多帧中执行。

5.3 分层路径寻找

另一种降低 CPU 开销的方式是 分层寻路。

基本思想是先在粗层级上找大致路径，再逐步细化。例如：

  • 先在省级范围搜索
  • 再缩小到市级
  • 再缩小到县级
  • 最后在局部区域进行精细寻路

这种方法特别适合大世界或超大场景。

6. Funnel 算法详解

参考：The Funnel Algorithm Explained

在实际游戏项目里，A* 或 Dijkstra 往往先给出的是一条”经过哪些节点 / 哪些三角形”的路径，但这条路径通常还不够平滑。特别是在 NavMesh 上，A* 找到的常常是一串三角形通道，此时还需要进一步把通道中的折线路径”拉直”，这就是 Funnel 算法 的作用。

6.1 Funnel 解决什么问题

Funnel 算法是计算几何里一个非常经典的最短路径算法。它讨论的不是”任意两点最短路”，而是一个更细的问题：

已知一条从 A 到 B 的可行路径 p，如何求一条与它绕障方式相同、但长度最短的路径？

这里”绕障方式相同”就是同伦（homotopy）。

6.2 什么叫”同伦”

可以把一条路径想成一根绳子，两端钉在起点和终点上：

  • 你可以在平面上拖动它
  • 但不能把绳子抬起来
  • 也不能穿过障碍物

如果一条路径可以这样连续变形成另一条路径，那么它们就是同伦的。

所以 Funnel 算法的目标不是全局最短，而是：在固定同伦类中，把路径”拉紧”。

这和机器人运动规划、导航网格 shortest path、mesh 上的 corridor shortest path 都是同一类问题。

6.3 为什么最短路径一定是折线

在二维带多边形障碍的环境里，固定同伦类下的最短路径一定是若干条线段拼起来的折线。

这个结论非常直观：

  • 如果路径中某一段是弯的
  • 那么把它拉直一定更短
  • 真正阻止继续拉直的，是障碍物边界

所以最终得到的路径，一定在一些关键拐点处贴着障碍物”折一下”，其余部分都是直线。

6.4 先把环境变成”三角形通道”

Funnel 算法通常建立在三角化基础上。做法是：

  1. 先把整个可行区域三角化。
  2. 找出原始路径 p 穿过了哪些三角形。
  3. 这些三角形连起来，就形成一条”通道（channel / corridor）”。

之后问题就从”整个环境里找路”变成：在这条固定通道里，找从 A 到 B 的最短折线。

因为同伦类已经由这条通道固定住了。

6.5 漏斗（funnel）到底是什么

漏斗是算法里维护的核心结构。它由三部分组成：

  • tail：左右边界重合的公共部分
  • left：漏斗左边界
  • right：漏斗右边界

其中 tail 的最后一个点叫 apex，也就是漏斗尖端。

可以这样理解：

  • tail 是已经确定属于最短路径的那一段
  • left 和 right 是当前通道对最短路径的左右约束
  • 漏斗包住的区域，就是”最短路径接下来可能经过的区域”

初始化非常简单：

tail = [A]
left = []
right = []

6.6 沿着原路径扫描通道

接下来沿着原路径 p 前进，每当路径穿过一条三角形边，就会遇到一个新的”门户（portal）”。每个 portal 都有两个端点：

  • 一个在当前方向下位于左侧
  • 一个位于右侧

我们把它们分别拿来更新 left 和 right。

本质上就是：每向前走一步，就用新的通道边继续收紧”最短路径可能存在的区域”。

6.7 更新漏斗时会发生什么

情况 1：新点让边界更紧

如果新出现的点比当前边界更靠内，那么旧边界就不再是最紧约束，需要被替换。也就是：

  • 原来的边界太”松”
  • 新点提供了更紧的包围
  • 于是把旧边界末端改成新点

这相当于漏斗口被进一步收缩。

情况 2：新点没有更紧，但必须扩展边界

有时候新点不会替换原边界，而是把边界继续往前延长。比如：

  • 当前左边界已经有一个折点
  • 新点没有把前面的边界压缩掉
  • 但通道继续往前走，左侧边界链必须延伸

这时直接把它追加到对应边界即可：

left.append(new_point)
# 或
right.append(new_point)

情况 3：一侧边界穿过了另一侧，apex 前进（最关键）

这是 Funnel 算法最核心的地方。如果某个新点不仅比当前右边界更靠左，甚至已经越过了左边界的一部分，那么说明：

  • 漏斗口已经在某处”夹闭”
  • 那个交汇点之前的公共部分已经确定属于最短路径
  • 需要把这部分并入 tail

也就是说，最短路径新增了一个拐点。这时会发生三件事：

  1. tail 增长
  2. apex 前进到新的尖点
  3. 左右边界以这个新 apex 重新开始组织

这一步就是”橡皮筋真正卡到障碍物上”的地方。

6.8 为什么 tail 一定属于最短路径

因为 tail 是左右边界重合的部分。换句话说：

  • 漏斗两侧在这段路径上没有任何自由度
  • 无论你怎么走，只要还留在同一通道里，都必须经过它

所以 tail 是已经被确定下来的最短路径前缀。这也是为什么算法把 tail 和左右边界分开存储会更清楚。

6.9 漏斗建完后，如何真正得到最短路

当整个通道都扫描完以后，漏斗就完整了。剩下的事情反而最简单：

  1. 把 tail 放进结果路径。
  2. 从当前 apex 直接连一条线到终点 B。
  3. 如果这条线没有穿出漏斗，说明可以直接到终点。
  4. 如果穿出了某一侧边界，就把那一侧对应的转折点加入路径。
  5. 把那个转折点当作新的 apex，继续朝终点尝试。

直到能直接连到 B 为止。所以最终的最短路径就是：

  • 一段已经确定的 tail
  • 加上若干个被漏斗逼出来的拐点
  • 最后接终点

6.10 直观理解：绳子与走廊

可以把通道想成一条狭长走廊，把路径想成一根带张力的绳子：

  • 左边界和右边界是走廊墙面
  • apex 是绳子当前被拉到最紧的位置
  • 每往前遇到一个 portal，就像走廊形状发生一次变化
  • 如果墙面逼得越来越紧，绳子就会在某个障碍顶点处”挂住”

那个”挂住”的点，就是新产生的最短路径折点。

所以 Funnel 算法其实就是：一边向前读通道，一边维护”绳子被拉紧后会挂在哪”。

6.11 最简伪代码

下面给一个非常简化的思路版伪代码：

tail = [start]
left = []
right = []

for portal in portals:
    l, r = portal.left, portal.right

    update_left_boundary(l)
    update_right_boundary(r)

    if boundaries_overlap():
        move_common_part_to_tail()
        reset_apex()

path = tail.copy()

while not visible(path[-1], goal, funnel):
    x = next_blocking_corner()
    path.append(x)

path.append(goal)

这里最难的不是框架，而是：

  • 如何判断”更紧”
  • 如何判断边界交叉
  • 以及更新后如何维护 tail/left/right

这些本质上都是二维方向测试（orientation test）和边界链裁剪问题。

6.12 算法评价

优点

  • 几何意义非常直观
  • 在导航网格上特别常用
  • 固定 corridor 后效率高
  • 结果就是实际最短折线，而不是近似折线

局限

  • 依赖已有 corridor / triangulation
  • 一般情况会遇到 U-turn、重复点、退化 portal 等边界情况
  • 更完整的版本通常会使用双端队列来维护 funnel，而不是简单的 tail + left + right 三数组

6.13 与 NavMesh 的完整关系

在游戏 AI 和机器人规划里，一个典型流程是：

  1. 在 NavMesh 上先用 A* 找到一串三角形
  2. 这串三角形形成 corridor
  3. 再用 Funnel 算法把 corridor 中心线”拉直”
  4. 输出一条平滑的最短折线路径

因此可以理解为：

  • A* 决定”走哪条通道”
  • Funnel 决定”在通道内怎么走得最短”

这也是为什么 Funnel 算法经常和 NavMesh 一起出现。

重点： 在现代游戏导航中，真正可用的路径通常不是 “A* 结束时的输出”，而是 A* 给出通道 + Funnel 做路径拉直 的组合结果。

如果只记一句话：

Funnel 算法就是在固定通道中，不断收紧左右边界，直到把路径”拉直”为同伦类中的最短折线。

它可以看成：

  • 一种 corridor shortest path 方法
  • 一种 固定同伦类最短路 方法
  • 也是 NavMesh 路径后处理最常见的几何算法之一

7. 总结

游戏导航可以概括为一句话：

先把地图变成图，再在图上高效搜索，最后在几何层面对路径做平滑和拉直。

其中最关键的设计点包括：

  • 单目标优先使用 A*
  • 多目标最近实例问题可使用 Dijkstra
  • 连续空间通常采用欧几里得启发
  • 大场景下导航图设计往往比搜索算法本身更关键
  • NavMesh 场景中常需要配合 Funnel 算法做路径后处理
  • 工程实现中要重点考虑优先队列、时间片和分层寻路
